VirtualBox 无线桥接的抓包盲区

29 Sep, 2026
目录
  • 网络协议
  • 问题与调试

网络协议

上层协议的整个报文，作为字节塞进下层协议的数据字段里，每一层会给同一份数据加上自己的头：

https://blog.csdn.net/dyx1993/article/details/113985648

应用层:   [HTTP 请求]
传输层:   [TCP头 | HTTP请求]
网络层:   [IP头 | TCP头 | HTTP请求]
链路层:   [帧头 | IP头 | TCP头 | HTTP请求 | 帧尾]
物理层:   发送

看了一通资料后，回顾过往场景，有了一些更深的理解

一，特定场景下浏览器经 SOCKS5 隧道进入靶标内网后，常见需求是用 Proxifier 限制可达 IP，避免误触其他资产导致暴露、丢失入口点。Proxifier 是一个工作在传输层的工具，负责拦截应用程序的 TCP/UDP socket 连接，转发给 SOCKS/HTTPS 代理。而 connect() 是一个 System Call 函数，它是网络编程中最核心的底层 API 之一，主要用于让客户端与服务器建立网络连接。

当访问被禁止 IP 时，浏览器调用 connect 发起连接请求，请求下行到传输层，Proxifier 命中 Block 规则，connect 直接失败返回。因此即使弹错误警告、重试，也都是本机行为，并不出网。

而当访问允许规则下的目标时，同样在传输层命中规则，但浏览器这次三次握手的对象实际是本机的 Proxifier，随后 Proxifier 与 SOCKS5 服务器建立新的 TCP 连接，再由 SOCKS5 服务器发送实际请求。

二，当 ping 发包时，ping.exe 调用系统 ICMP，由内核构造请求报文。它工作在网络层，随后在数据链路层被封装成帧，结构大致为帧头、IP头、ICMP报文、帧尾。一次 ICMP 只有两帧，若 ARP 缓存为空，前面还会先出现一对 ARP。

nmap 的 -sT 走操作系统的 connect()，由内核协议栈完成握手；-sS 则由 nmap 自己构造原始帧、通过 Npcap 直接注入网卡收发，需要 raw 权限。一开始怀疑是防火墙拦截或管理员权限问题：切到管理员 PowerShell、关闭防火墙、再装上 Npcap，全都试过，扫描仍然没有结果。但 ping 和网络又是通的。

PS F:\tools-new\recon\nmap-win> ping 192.168.0.100

正在 Ping 192.168.0.100 具有 32 字节的数据:
来自 192.168.0.100 的回复: 字节=32 时间<1ms TTL=64
来自 192.168.0.100 的回复: 字节=32 时间<1ms TTL=64

用 Wireshark 抓包，发现靶机正在疯狂发送 DHCP 请求。

VirtualBox 文档中描述多数无线网卡不支持混杂模式，所以无线桥接时 VirtualBox 会做 MAC 翻译，出站帧的源 MAC 替换为宿主机无线网卡的 MAC，入站帧按 IP 归属替换目的 MAC 后递给 VM。于是有了推测，VM 到宿主机的回包在本机内部被短路，这条路径恰好绕开了 Npcap 挂靠的捕获点。

靶机的真实 MAC 是 08:00:27:xx:xx:xx，而以太网帧源 MAC 和 Wireshark 里 ARP 显示的都是无线网卡的 MAC。靶机发往局域网的帧都被 VirtualBox 改写为宿主机 MAC 后才上线，靶机在局域网上被网关认同为宿主机；但 arp -a 又能看到真实 MAC，ping 也能找到对方的 MAC 并得到响应，同一台机器在链路上同时存在两个 MAC 版本。

Nmap 的 SYN 扫描会先做 ARP 解析：独立发 ARP 广播、靠 Npcap 独立抓应答，拿到 MAC 后才构造帧，通过 Npcap 把帧直接注入网卡，然后等 SYN-ACK 或 RST。而在这个环境里，第一步就卡死了。

这次问题的本质是 Npcap 抓包、注帧路径和正常协议栈不同，无线桥接的内部短路又绕开了 Npcap 的捕获点，于是出现扫不通的情况。修复非常简单，靶机网卡从桥接模式切换为其他网络模式，其余什么都不用动。
